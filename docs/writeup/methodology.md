## Research approach

This study is a quantitative, controlled experiment. Remediation suggestions
were generated by three large language models (LLMs) for 15 injected dbt
failures, each presented at three levels of structured context. The
suggestions were then scored on four dimensions: technical accuracy, root
cause correctness, actionability and specificity. The research questions are
answered by comparing these scores across context levels, failure categories
and models, as set out in the proposal (§7.1).

## Experimental environment

A small e-commerce pipeline was built with dbt-core 1.12 and DuckDB:

- **Raw tables:** customers, orders and payments, generated from a fixed
  random seed. There are 200 customers, 600 orders and 636 payments, each
  with a `loaded_at` timestamp.
- **Sources:** declared with freshness thresholds.
- **Models:** staging models (`stg_customers`, `stg_orders`, `stg_payments`)
  and marts (`dim_customers`, `fct_orders`).
- **Exposures:** two dashboards downstream of the marts.
- **Tests:** dbt's built-in tests (unique, not_null, relationships,
  accepted_values), source freshness, and three small custom generic tests:
  a row-count range, a null-rate threshold, and equal row counts between
  `fct_orders` and `stg_orders` (D14, D15).

The custom tests were written in the project rather than taken from dbt
packages, so that the full test SQL is visible in the artefacts.

Ingestion and transformation were run separately, as in a production
warehouse where dbt does not load raw data (D13). The raw tables were loaded
first, then the transformation job (`dbt build`) ran, then
`dbt source freshness`. On clean data the build passed all 32 nodes.

Each scenario was built the same way (D16):

1. Copy the clean project.
2. Run it once on clean data, so the warehouse holds "yesterday's" tables.
3. Apply one deterministic fault.
4. Run ingestion, `dbt build` and `dbt source freshness`.

Every run was checked against the failures the scenario was designed to
cause, and all 15 matched on the first full run. A single reference time
(13 October 2026, 18:00 UTC) and seed (42) were used for all scenarios, and
the scenarios were frozen after this.

**Context artefacts.** For each scenario the following were saved from the
real dbt run: `run_results.json`, the relevant manifest nodes and the
compiled SQL of the failing model.

**What the context shows.** The models and sources described in the context
were chosen only from the observed failure (the failing test, its model, or
the stale source), never from the known root cause, so the context cannot
point to the answer. An automated check confirmed that no prompt contains the
category name, the scenario title, the words "root cause", or any sentence of
the reference fix (D16).

**Root-cause types.** Of the 15 root causes, 11 lie in upstream data, 3 in
dbt code and 1 in configuration (D17). This reflects where data-quality
failures usually start, but it means the design is unbalanced by cause type.
For the three code faults the faulty SQL is visible from the partial level
onwards. Cause type is therefore reported descriptively as a possible
moderator, not tested as a factor.

**Reference fixes.** For every scenario the researcher wrote a
gold-standard remediation (root cause, exact fix with files and SQL,
verification step) against the actual artefacts, at the time the fault was

## Prompt framework

The five-part cumulative prompt from the proposal (§7.4) was implemented as
one Python function that takes a scenario and a context level, and has no
model argument (D20). The same text therefore went to all three models, as a
single user message with no system prompt.

| Level | Parts | Content |
|---|---|---|
| Minimal | 1 + 5 | Failure description; remediation request |
| Partial | 1 + 2 + 5 | + model metadata (materialisation, schema, column definitions, model SQL) |
| Full | 1 + 2 + 3 + 4 + 5 | + lineage (upstream and downstream nodes, edge types) and recent history |

**The five parts:**

- **Parts 1–3** were rendered from the real dbt artefacts.
- **Part 4 (recent history)** is synthetic and labelled as such in the
  scenario files. It lists the relevant change, two unrelated but true
  changes, one past incident and a recent-run metric (D16).
- **Part 5** asks for four fixed headings: Root cause, Fix, Verification and
  Assumptions. It also asks the model to label anything not given in the
  prompt as an assumption, and allows fixes outside dbt ("say what should
  change and where"), because most root causes are upstream. Answers were
  asked to stay under 500 words, not counting code (D20).

**Wording choices:**

- Headings are unnumbered, so a minimal prompt does not reveal that other
  parts exist.
- The build command is shown as plain `dbt build`, so that the prompt does
  not reveal that the raw tables are dbt seeds, i.e. that the pipeline is
  simulated (D19).

**Prompt size:** about 440–710 tokens at minimal, 610–1,960 at partial and
1,230–2,910 at full (estimated as characters / 4).

## Models and run settings

**Table M2. Models.**

| Role | Model ID used | Access |
|---|---|---|
| OpenAI GPT-5 series | `gpt-5.5-2026-04-23` (dated snapshot) | OpenAI API |
| Anthropic Claude Sonnet | `claude-sonnet-5-5` | Anthropic API |
| Local open-weight model | `llama3:8b` (Ollama digest `365c0bd3c000`) | Ollama 0.40.3, on the researcher's laptop |

**Model versions.** Model IDs were pinned before the main run, and every
call logged the version string the API reported (D2). All 405 answers came
from the pinned versions.

**Settings, the same for every model:**

- **Temperature 1.0** (D3). This was the only value all three models
  accepted: Claude Sonnet 5.5 rejects any other temperature.
- **Maximum output 2,048 tokens.**
- **Reasoning or "thinking" at its lowest setting** on both cloud models
  (D4), because llama3:8b has no reasoning mode and hidden reasoning tokens
  would count against the output limit. Results therefore describe the
  models' direct answers, not their reasoning-mode performance.
- **No automatic fallback** to another model (D5).
- **Context window for llama3:8b set to 8,192 tokens** on every call. A test
  showed that Ollama's smaller default window silently drops the middle of a
  long prompt, which would have turned a full prompt into a minimal one (D1).

**Repetitions and order.** Each scenario × level × model condition was run
three times: 15 × 3 × 3 × 3 = 405 calls. The OpenAI and Anthropic APIs take no
random seed. llama used seeds 42, 43 and 44 for repetitions 1–3 (D11, D21).
The order of all 405 calls was shuffled with a fixed seed, and each model
worked through its own calls in that order. Time of day was therefore not
confounded with scenario or level.

**Collection.**

- Every answer was stored as returned, with run settings, token counts,
  latency, stop reason and the SHA-256 hash of the prompt (D21).
- No answer was re-run because it looked poor.
- The runs took place on 19, 23 and 25 October 2026. The OpenAI account ran
  out of credit part-way through, and the 62 missing GPT calls were completed
  with the same pinned snapshot once credit was added. Because the order was
  shuffled, these 62 calls were a random subset of conditions.
- The total cost was US$6.63.

## Evaluation framework

### Human-scored dimensions

**Rubric.** Technical accuracy (0 / 0.5 / 1), root cause correctness (0 / 1)
and actionability (1–3) were scored with the rubric and anchors in the
evaluator pack (proposal §7.5, Appendix A; final terms in D9). Two rules were
added to the rubric:

- A score of 3 for actionability requires the root cause, the exact fix
  location with code, the affected downstream models and a verification
  step.
- References to models or columns that do not exist are noted, and the fix
  is scored on how it would actually behave.

**Blinding (D7, D24).** Each answer received a random item ID, such as
`RC02-05A`. Neither part of the ID reveals the model or the context level.
Raters saw, for every item:

- the full scenario (failure, metadata, lineage, history);
- the reference fix;
- one suggestion labelled Model A, B or C.

They never saw the prompt the model received, so they could not tell the
context level, which is the main independent variable. The key linking item
IDs to models and levels was held only by the researcher.

**Raters.** Two practising data engineers were the expert evaluators.
[Describe the panel's experience as ranges, as promised in the evaluator
pack, e.g. "x–y years of data engineering experience".]

- **Which answers (D6).** Scoring all 405 answers would have taken each
  expert 13–20 hours, against the 4–6 hours stated when they gave consent.
  The experts' set was therefore one randomly chosen repetition of every
  scenario × level × model: 135 answers, covering every design cell.
- **How the work was split (D30).** To fit the submission date, the 135
  answers were divided so that each expert scored 90:
  - 45 answers scored by both experts, used to measure their agreement;
  - 45 answers scored by each expert alone.

  In every part, each model appears once per scenario and each level 15
  times, so neither expert's own share favours a model or a level. Each
  expert's answers were grouped by scenario, so a scenario was read once and
  its six answers scored in a row.

**Calibration (D23, D31).** Before the main scoring, each expert scored the
same five practice answers on their own and returned them. The researcher
compared the two sets and sent both experts a note on where they differed
and how such cases should be scored [date: ___]. The proposal planned this as
a joint session; it was done by email to fit the submission date (D31). The
practice answers came from a separate pilot scenario (PL01: duplicate
customers after a CRM account merge), which is not one of the 15 scenarios,
and are excluded from the results.

**No drift check.** The proposal planned a midpoint check in which each
expert re-scores earlier answers, to catch scoring standards shifting over a
long evaluation period (§7.6). Scoring took place over [n] days instead of
the planned four weeks, so this check was dropped (D30).

**Tools (D10, D24).** Each expert received one offline HTML page: nothing to
install, autosave in the browser, CSV export. The researcher used a terminal
scoring tool. Imports were checked: every row must belong to the right
rater, carry the right status and match the item at that position.

### Specificity (automated)

Specificity is the cosine similarity between an answer and its scenario's
reference fix, using the sentence-transformers model
`all-mpnet-base-v2` (Reimers & Gurevych, 2019) at a pinned revision, computed on a CPU so the results are deterministic (D26). Two
details matter:

- **Chunking.** The embedding model reads at most 384 tokens and ignores the
  rest. Most answers are longer: every GPT and Claude answer and 76% of llama
  answers. Without correction, a cloud answer would be judged on its first
  third and a llama answer on most of its text. Answers were therefore split
  at paragraph, line or word boundaries into chunks of up to 382 tokens. The
  chunk vectors were then averaged, weighted by token count.
- **What is compared.** The answer without its Assumptions section, against
  the reference fix's root cause, fix and verification. The rubric does not
  score assumptions, and the reference fix has none.

**Bands.** The proposal's provisional bands (≥ 0.75 high, 0.5–0.75 moderate,
< 0.5 low) were checked on the nine pilot answers before the main analysis,
using a rule set in advance. The rule compared each pilot answer's
similarity to its own reference fix with its similarity to the 15 unrelated
reference fixes.

- **The 0.75 cut held.** No answer about a different incident reached it.
- **The 0.5 cut did not.** Most answers about a different incident scored
  above 0.5.
- **Revised lower cut.** It was moved to 0.69, the 95th percentile of the
  pilot's wrong-scenario similarities. "Low" therefore means "no more similar
  to the reference fix than an answer about a different incident" (D26).
- **Bands are descriptive only.** All statistical tests use the continuous
  score.

**Validity checks** on the main run:

- Specificity correlated with the share of the scenario's key entities that
  an answer named (Spearman ρ = 0.64).
- It did not correlate with answer length (|ρ| ≤ 0.15 within each model).
- For 78% of answers, the closest of the 15 reference fixes was their own.

### Hallucinations

**Definition.** A hallucination is a model, source, column, file, dbt
setting or SQL function that an answer states as existing but that does not
exist in the scenario's project, in dbt or in DuckDB (D27).

**Automated candidates.** An automated check extracted the names each answer
refers to (`ref()` and `source()` targets, model-like names, `table.column`
references, columns in its SQL and YAML, file paths and code identifiers) and
compared them with the scenario's real models, sources, columns, tests and
files. Some names were not flagged as candidates:

- names the answer defines itself, such as aliases, new columns or new files;
- names that appear in the prompt;
- DuckDB keywords and functions;
- names the answer lists under Assumptions, which were counted as assumed.

**Review.** The researcher reviewed every candidate blind to model and
level, and gave it a verdict:

- H: hallucination;
- C: conditional, i.e. a hedged guess or an example;
- N: a new object the answer proposes;
- F: false positive.

Only H counts as a hallucination. The precision of the automated check is
the share of candidates confirmed as H. Its recall was estimated by reading
27 answers in full, 3 per model × level, drawn with a fixed seed.

**AI assistance in the review.** An AI assistant (Claude) pre-classified each
candidate and pre-read the 27 recall answers. It worked from the blinded item
IDs and the scenario's real names, and gave a reason for each suggestion. The
researcher then confirmed or changed every suggestion, and only confirmed
verdicts were analysed. [Report how many suggestions the researcher changed:
count "changed to" in the `reviewer_note` column.] The assistant belongs to
the same model family as one of the three models studied; the blinded IDs
hid which model wrote each answer.

**Reported as two rates:**

- the share of answers with at least one hallucination;
- hallucinations per 100 checked references.

The second rate matters because llama names far fewer entities (median 5 per
answer, against 12–15 for the cloud models), so it has fewer chances to name
a wrong one.

### False confidence

The proposal names false-confidence risk (RQ4) but gives no measure for it.
It was measured as follows (D28):

- **Hedge words.** The Root cause section of each answer was scanned for
  hedge words from a fixed list ("likely", "may", "might", "appears", "cannot
  confirm", …). A root cause stated with no hedge word at all counts as
  *asserted*.
- **False confidence** is a wrong diagnosis (root cause scored 0) that is
  asserted. It is reported as a rate, as a share of all wrong diagnoses, and
  against the asserted share of correct diagnoses. A well-calibrated model
  should hedge more when it is wrong.

A word list is a proxy, not a validated confidence measure. It misses
hedging that uses other words, and it counts some non-hedging uses.

## Analysis

**Unit of analysis (D29).** Following the proposal (§7.3), the three
repetitions of each condition were reduced to their median. That gives one
value per model × scenario × level: 45 values per model and dependent
variable, 3 in each level × category cell. This applies to specificity. The
human-scored dimensions have one scored repetition per cell (the experts'
135 answers, D30): the mean of both experts for the 45 shared answers and the
single expert's score for the other 90. They therefore have the same 45
values per model, but each is one answer rather than a median of three.

**Main analysis.** For each model and dependent variable, a two-way ANOVA
was fitted with context level, failure category and their interaction:
`y ~ level × category`, Type II sums of squares, partial η² as the effect
size. As proposed, the three models were analysed separately, with model not
a factor. The design is balanced, so Types I–III give the same result.

Two additions were made to the proposal's plan:

1. **Holm correction.** The four dependent variables test the same
   hypothesis, so p-values were Holm-corrected across them within each model
   and effect (Holm, 1979). Uncorrected p is reported alongside.
2. **Rank-based checks.** The ANOVA assumes normal residuals and equal
   variances, which were checked with Shapiro-Wilk and Brown-Forsythe tests
   (Shapiro & Wilk, 1965; Brown & Forsythe, 1974). These assumptions were
   expected to fail for the human dimensions, which take only two or three
   values. Kruskal-Wallis tests were therefore run for level and for category
   (Kruskal & Wallis, 1952). In addition, the same 15 scenarios appear at all
   three context levels, so the 45 values are repeated measures. The
   proposal's ANOVA does not model this, so a Friedman test with scenario as
   the block was added for the level effect (Friedman, 1937). A context effect
   is called robust only where the ANOVA and the Friedman test agree.

**Post-hoc comparisons.** Tukey HSD compared the three context levels
(Tukey, 1949), on all 45 values and within each failure category as
proposed. Within a category there are only three values per level, so those
comparisons have very little power and are read as descriptive.

**RQ3: failure categories.** Category means per model, the ANOVA's category
effect, and Kendall's W were used. Kendall's W measures whether the three
models rank the five categories in the same order (Kendall & Babington Smith,
1939).

**RQ4: reliability.** These rates were computed per answer over all 405
answers, not on medians:

- misdiagnosis rate (root cause scored 0);
- false-confidence rate;
- confirmed hallucination rates;
- context-window use.

Each is reported by model, context level and failure category.

**Agreement.** Inter-rater reliability was measured with Cohen's kappa over
the full scale, as proposed (Cohen, 1960). Quadratic-weighted kappa (Cohen,
1968) and percentage agreement were reported alongside, and interpreted with
Landis and Koch (1977). The two experts were compared on the 45 answers both
scored. Where they disagreed, both scores were kept and averaged rather than
resolved (D9).

**Power.** With three values per cell and 30 residual degrees of freedom,
small interaction effects cannot be detected. The pilot did not include a
variance estimate (D23). Effect sizes and confidence intervals are therefore
reported alongside p-values.

**Tools.** Python 3 with pandas, SciPy and statsmodels. All analysis is in
`scripts/analyse.py`, and every random choice is seeded (seed 42).

## Ethical considerations

Ethical clearance was granted by the IIE's research ethics committee
(reference CSREC/st10359034/019).

- **Data sent to models.** Every prompt contained only the synthetic project
  and scenarios. No real company, system, customer or personal data was sent
  to any model. Each submission is logged with its provider, data type and
  date, as the proposal requires (§8.2).
- **Evaluators.**
  - Both evaluators gave written informed consent [confirm both forms are
    signed]. The evaluator pack
    explained the time required (4–6 hours) and the right to withdraw: scores
    are deleted if consent is withdrawn before 11 December 2026, after which
    anonymised scores are kept.
  - Evaluators appear in the data only as "Evaluator 1" and "Evaluator 2".
  - Experience is reported only as ranges for the panel as a whole.
  - Signed consent forms are stored outside the research repository
    [location].
  - Evaluators agreed not to use AI tools when scoring.
- **Storage.** All data is held on the researcher's password-protected
  laptop and in a private GitHub repository. Access is limited to the
  researcher, and the supervisor on request. API keys were never committed.
  A data logbook records every dataset's creation, nature, location and
  changes (§8.5).
- **Misleading advice.** Following §8.3, model suggestions are treated as
  proposals that need human review, never as actions. The study measures how
  often they are wrong (misdiagnosis, false confidence and hallucination),
  not whether they should be applied.
