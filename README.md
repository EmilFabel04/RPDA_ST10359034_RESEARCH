# Evaluating LLM-Generated Remediation Suggestions for Data Quality Failures in dbt Pipelines

RPDA8411 research project. **Research question:** how does the richness of
structured dbt context (minimal / partial / full) affect the quality of LLM
remediation suggestions for dbt data-quality failures, across 5 failure
categories and 3 LLMs?

Design: 3 context levels × 5 failure categories (3 scenarios each = 15
scenarios) × 3 models × 3 repetitions = 405 LLM calls.

Methodological decisions and deviations from the proposal are recorded in
[`docs/decisions_log.md`](docs/decisions_log.md).

## Layout

```
core/            shared config (.env loading) + uniform LLM client
scripts/         one script per step (run from the project root)
dbt_project/     dbt + DuckDB e-commerce project            (Step 2)
data/scenarios/  15 injected-failure scenarios + artefacts   (Step 3)
prompts/         5-part cumulative prompt builder            (Step 4)
results/         raw LLM outputs, scores, metrics, figures   (Steps 5-8)
tests/           unit tests (pytest)
docs/            decisions log, data logbook, prompt examples, write-up drafts
```

## Step 1 — Environment

Requirements: macOS, Python 3.12, [Homebrew](https://brew.sh).

```bash
# 1. Python environment
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-lock.txt     # exact versions used in the study

# 2. Local model
brew install ollama
brew services start ollama               # runs Ollama in the background
ollama pull llama3:8b

# 3. API keys
cp .env.example .env                     # then paste your keys into .env

# 4. Check all three models answer
python scripts/test_connection.py
```

`test_connection.py` checks that the pinned model IDs exist, sends one prompt
to all three models, tests whether temperature 0.7 is accepted, and shows
that llama3 reads the full prompt with `num_ctx=8192`.

**Checkpoint 1 passed 2026-10-13:** all three models answer with the pinned
settings; llama3 reads the full prompt at `num_ctx=8192`. Claude Sonnet 5.5
rejects temperature 0.7, so all models use 1.0 (see decisions log D3).

## Step 2 — dbt + DuckDB project

```bash
python scripts/build_clean.py     # generate seeds, dbt seed, dbt build, dbt source freshness
```

`dbt_project/` is a small e-commerce warehouse in DuckDB (`dbt_project/ecommerce.duckdb`):

```
raw.raw_customers ─▶ stg_customers ─┐
raw.raw_orders    ─▶ stg_orders    ─┼─▶ dim_customers
raw.raw_payments  ─▶ stg_payments  ─┴─▶ fct_orders
```

- Seeds are generated by `core/seed_data.py` (seed 42, timestamps relative to
  now so freshness passes; `--as-of` reproduces an earlier run exactly).
- Tests: unique, not_null, relationships (fct_orders.customer_id →
  dim_customers, stg_payments.order_id → stg_orders), accepted_values
  (order status, payment method), row count (stg_orders 500–1,000 rows;
  fct_orders must equal stg_orders), null rate (email ≤ 5%), and source freshness (orders/payments warn 6 h, error 12 h;
  customers warn 24 h, error 48 h).
- Every source and model column has a description.

To run dbt by hand: `cd dbt_project && ../.venv/bin/dbt build --profiles-dir .`
(run `dbt seed` first).

## Step 3 — 15 failure scenarios

```bash
python scripts/inject_failure.py          # refuses to overwrite; --force to regenerate
```

Definitions: `core/scenario_defs.py` (5 categories × 3 root causes; fault,
expected failures, synthetic history, gold standard). Output per scenario in
`data/scenarios/<id>/`:

| file | contents |
|---|---|
| `scenario.json` | prompt parts 1–4 as text, gold-standard remediation, token estimate |
| `ground_truth.json` | root cause, fault diff / data change, expected vs observed failures, fix targets, valid entity names |
| `run_results.json`, `sources.json` | dbt artefacts of the failing run |
| `manifest_nodes.json` | models, tests, sources, exposures + parent/child maps |
| `compiled/`, `logs/`, `relation_columns.json`, `fault.diff` | compiled SQL, dbt output, warehouse columns, code/config diff |

`data/scenarios/index.csv` lists all 15 with their observed failures.

## Step 4 — Prompt builder

```bash
python scripts/show_prompts.py SD01                  # print SD01's three prompts + size table
python scripts/show_prompts.py SD01 --measure-llama  # also exact llama3 token counts (local)
```

`prompts/builder.py` assembles five cumulative parts; part 5 (the task) is the
same text in every prompt and every model gets the identical string:

| level | parts | contents |
|---|---|---|
| minimal | 1 + 5 | intro + failure report (dbt build / freshness output) + task |
| partial | 1 + 2 + 5 | + metadata of the failing models / sources (columns, types, tests, SQL) |
| full | 1 + 2 + 3 + 4 + 5 | + lineage (DAG, upstream columns, downstream impact) + recent history |

The three SD01 prompts are saved in `docs/prompt_examples/`. Tests:
`tests/test_prompt_builder.py` (parts per level, order, shared task, no model
argument, no answer leaks, every prompt fits llama's context window).

## Step 5 — Running the experiment (405 calls)

```bash
python scripts/run_experiment.py --dry-run          # plan + cost/time estimate, no calls
python scripts/run_experiment.py --scenarios SD01   # one scenario (27 calls)
python scripts/run_experiment.py                    # everything not yet done (asks "yes" first)
python scripts/run_experiment.py --summary          # what has been saved so far
```

- Output: `results/raw_outputs.jsonl`, one line per answer (run ID, scenario,
  level, model, rep, prompt version + SHA-256, model version reported by the
  API, text, tokens, latency, stop reason, cost, settings).
- Resumable: saved run IDs are skipped. Failed calls go to `results/errors.jsonl`
  and are retried on the next run. Ctrl-C stops after the calls in progress.
- Refuses to run if saved answers came from a different prompt or model ID.
- Calls are shuffled with the global seed; the three models run in parallel.
- Tests: `tests/test_run_experiment.py` (design size, seeded order, same
  prompt across models, llama seeds per rep, version guard, resume).

## Step 6 — Blinded scoring

```bash
python scripts/inject_failure.py --pilot          # calibration scenario PL01 -> data/pilot/
python scripts/run_experiment.py --pilot          # its 9 answers -> results/pilot/
python scripts/prepare_scoring.py                 # blinding key, assignments, scoring pages
python scripts/make_scenario_check.py             # scenario check page for the evaluators (O1)
python scripts/make_scenario_check.py --summary   # what the returned checks flagged
python scripts/score_tool.py                      # you: score all 405 (PROVISIONAL), resumable
python scripts/import_scores.py expert_1 ~/Downloads/scores_expert_1.csv   # an expert's export
python scripts/make_mock_scores.py                # MOCK placeholders until real scores exist
```

| file | what | who sees it |
|---|---|---|
| `results/blinding_key.json` | item id → run, model, level, rep | researcher only |
| `results/scoring/assignments.json` | each rater's items in order | researcher only |
| `results/scoring/pages/score_expert_1.html`, `_2.html` | offline scoring page: 90 items each, 45 shared + 45 own, grouped by scenario (D30) | send to each evaluator |
| `results/scoring/pages/calibration.html` | the 5 pilot samples for the calibration call | evaluators + researcher |
| `results/scoring/pages/scenario_check.html` | the 15 scenarios + reference fixes: realistic? fix correct? (no LLM answers) | send to both evaluators first |
| `results/scoring/scenario_check_expert_N.csv` | their returned checks | — |
| `results/scores_<rater>.csv` | real scores (researcher: status PROVISIONAL) | — |
| `results/mock/scores_<rater>.MOCK.csv` | random placeholders, never results | — |

Evaluators open their HTML file in any browser (nothing to install). Scores
autosave in the browser; **Export CSV** downloads `scores_expert_N.csv`, which
they email back. **Load CSV** restores a previous export (e.g. on another
computer). Each item shows the full scenario and the reference fix, never the
prompt, and the suggestion only as "Model A/B/C".

The researcher's labels: every researcher score is status `PROVISIONAL`;
anything built from it is labelled "Provisional researcher scores — expert
evaluation pending". Tests: `tests/test_scoring.py`, `tests/test_scenario_check.py`.


## Step 7 — Automated metrics

```bash
python scripts/compute_metrics.py --bands          # first: specificity bands vs the pilot (D23, D26)
python scripts/compute_metrics.py                  # all 405 answers, ~1 min on CPU
python scripts/compute_metrics.py --show RC02-05A  # print one blinded answer (for the reviews below)
```

The first run downloads `sentence-transformers/all-mpnet-base-v2` (~420 MB,
revision pinned in `core/metrics.py`); later runs load it from the local cache.

`results/auto_metrics.csv`, one row per answer:

| column(s) | meaning |
|---|---|
| `specificity` | cosine similarity to the scenario's gold standard (all-mpnet-base-v2; chunked, D26) |
| `specificity_band` | high ≥ 0.75, moderate ≥ 0.69, low below (descriptive only; 0.69 from the pilot, D26) |
| `sim_other_mean`, `sim_other_max`, `own_gold_rank` | similarity to the other 14 gold standards; rank 1 = own gold is the closest |
| `key_entity_recall` | share of the scenario's key entities the answer names (a transparent cross-check) |
| `refs_checked`, `refs_unknown`, `refs_assumed` | entity references checked against the project; not found; not found but stated as an assumption |
| `hallucination_candidates`, `hallucination_auto` | unknown references not stated as assumptions (count, any) — before review |
| `hallucinations_confirmed` | references the reviewer marked `H`; empty until every candidate of that answer has a verdict |
| `hedges_root_cause`, `root_cause_asserted`, `hedges_per_100w`, `n_assumptions` | hedging, for false confidence (D28) |
| `words`, `input_tokens`, `output_tokens`, `all_headings`, `truncated` | length, context-window use, format |

**Two short reviews for the researcher** (blinded item ids only; use `--show`
to read an answer):
1. `results/hallucination_review.csv`: one row per candidate. Fill `verdict`:
   `H` hallucination (stated as existing, does not exist), `C` conditional
   (a hedged guess or example), `N` new (something the answer proposes to
   create), `F` false positive. Re-run `compute_metrics.py`; verdicts are kept.
2. `results/hallucination_recall_sample.csv`: 27 answers (3 per model × level).
   Read each in full, put `yes` in `checked`, and list in `missed_entities`
   any non-existent model, column, file, setting or function stated as fact
   that is not already in the review file for that item.

**AI-assisted way to do both (D27):** an AI assistant has pre-filled suggestions
with reasons (`results/hallucination_suggestions.csv`,
`results/hallucination_recall_suggestions.csv`). Go through them one at a time;
Enter accepts, or type your own answer; it saves after every row and resumes:

```bash
python scripts/confirm_suggestions.py            # the 62 flagged references (~15-20 min)
python scripts/confirm_suggestions.py --recall   # the 27 recall answers, read each in full (~30-45 min)
```

Tests: `tests/test_metrics.py`, `tests/test_confirm_suggestions.py`.


## Step 8 — Analysis

```bash
python scripts/analyse.py          # real score files -> results/analysis/ + results/figures/
python scripts/analyse.py --mock   # MOCK scores and review -> results/mock/analysis/ + results/mock/figures/
```

Each part runs as soon as its inputs are complete; until then `report.md`
lists it as pending. Specificity, context-window and hallucination-candidate
results are automated and always run. Methods: decisions log D29.

| needs | gives |
|---|---|
| `results/scores_researcher_provisional.csv` (all 405) | technical accuracy, root cause, actionability: ANOVA, Tukey, misdiagnosis and false-confidence rates |
| `results/scores_expert_1.csv` + `_2.csv` | kappa between experts, midpoint consistency, researcher vs experts, the same ANOVA on the expert subset |
| verdicts in `results/hallucination_review.csv` | confirmed hallucination rates, precision of the check |
| `results/hallucination_recall_sample.csv` read (`missed_entities` separated by `;`) | recall of the check |

`results/analysis/`:

| file | contents |
|---|---|
| `report.md` | everything below in readable form, with the data labels |
| `cells.csv` | the unit of analysis: one value per model × scenario × level (median of 3 repetitions) |
| `descriptives_*.csv` | n, mean, SD, median, quartiles by level, category, category × level, root-cause type × level |
| `anova.csv`, `assumptions.csv` | two-way ANOVA (level × category) per model and DV, partial η², Holm-adjusted p; Shapiro-Wilk, Levene |
| `tukey.csv`, `nonparametric.csv` | Tukey HSD between levels (all categories and within each); Kruskal-Wallis, Friedman |
| `consistency.csv` | RQ3: Kendall's W, do the models rank the five categories alike |
| `rates.csv`, `hallucination_check.csv`, `context.csv` | RQ4: misdiagnosis, false confidence, hallucinations (candidates, confirmed, per 100 references), check precision / recall, prompt and answer sizes |
| `agreement.csv`, `rep_spread.csv` | Cohen's kappa (and quadratic-weighted), % agreement; spread of the 3 repetitions |
| `*_experts.csv` | the same tests on the experts' scores (one repetition per cell) |

Figures: `fig1_context_effect.png` (means ± 95% CI by level), `fig2_category_level_heatmaps.png`,
`fig3_specificity.png` (every answer, with the bands), `fig4_reliability.png` (hallucination,
misdiagnosis, false confidence by level).

**Labels.** Every table row has `data_label`, and every figure has a footer:
"Provisional researcher scores — expert evaluation pending" on anything built
from the researcher's scores, "Automated metric" on specificity and the
automated rates, and "MOCK DATA" (plus a watermark on figures) on everything from
`--mock`. Mock outputs go only to `results/mock/` and are not committed.

Tests: `tests/test_analysis.py`.
